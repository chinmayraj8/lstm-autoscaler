No CI existed anywhere in this project before this step -- every prior

## What changed

**`.github/workflows/ci.yml`** (new). Three separate jobs, not one:

- `lint` -- `ruff check src/ tests/`, using this repo's new
  `pyproject.toml` rule selection.
- `test-fast` -- installs everything in `requirements.txt` EXCEPT
  `tensorflow` (filtered out with `grep -v` at install time, not a
  separately maintained file, so it can't silently drift from
  `requirements.txt`), plus `requirements-dev.txt`, then runs
  `pytest tests/ --ignore=tests/test_api_shadow.py`.
- `test-full` -- installs the complete, unmodified `requirements.txt` +
  `requirements-dev.txt` (the exact pinned set the real Docker image
  uses -- Dockerfile parity, not a separate CI-only dependency set), then
  runs the complete suite including `test_api_shadow.py`.

All three trigger on push and PR to `main`. Python 3.11 in every job, to
match the Dockerfile's `python:3.11-slim` base exactly.

**Why split `test-fast`/`test-full` at all, rather than one job**:
`tests/conftest.py` has said, since it was written, that this suite "is
meant to run fast, in CI, without a TensorFlow install" (because
`src/autoscaler/__init__.py` only eagerly imports
config/calibration/data/decision/simulation/shadow/metrics_source/live_loop,
none of which need TensorFlow -- see that file's own docstring). That
was a documented design intent nothing had ever actually exercised until
this step. `test-fast` is what makes it a real, checked fact rather than
an assertion in a comment. Only `tests/test_api_shadow.py` needs
TensorFlow (it imports `src/api/main.py`, which imports `_build_lstm_model`
at module level), so it's the one file excluded from `test-fast` and the
reason `test-full` exists at all.

**`pyproject.toml`** (new). `[tool.ruff.lint] select = ["E4", "E7", "E9", "F"]`
-- pyflakes + pycodestyle's error classes only (unused imports/variables,
undefined names, syntax errors). Deliberately narrower than ruff's own
default rule selection: a bare `ruff check .` with no config pulls in a
much broader set (pyupgrade, flake8-comprehensions, flake8-simplify,
flake8-datetimez, flake8-bandit, and more -- 149 findings on this
codebase without this config file) that flags this project's own
intentional, documented patterns as bugs -- most importantly the
"log it, move on" broad `except Exception:` convention used throughout
`live_loop.py` and elsewhere, which flake8-bandit's `BLE001` would flag
on every occurrence. Locking the rule set in a committed config file
also means CI won't silently get stricter (or looser) on a future ruff
upgrade the way a bare `ruff check .` would.

**12 pre-existing lint findings fixed** (all genuinely dead code /
harmless, reviewed individually before fixing, nothing touching
actuation or decision logic):
- 9 unused imports (`src/api/demo_client.py`, `src/api/main.py`,
  `src/autoscaler/arima_baseline.py`, `src/dashboard/prepare_replay_data.py`,
  `tests/test_arima_baseline.py`, `tests/test_calibration.py`,
  `tests/test_live_loop.py`, `tests/test_shadow_store.py`)
- 1 f-string with no placeholders (`src/api/demo_client.py`)
- 1 genuinely dead local variable, `t0 = time.time()` in
  `src/dashboard/prepare_replay_data.py` -- assigned, never read;
  `wall_clock_secs` (returned by `_train_lstm` itself) was already doing
  the actual timing
- 1 import-order issue in `src/api/demo_client.py` (`import warnings`
  after a `sys.path.insert` statement) -- moved `import warnings` up
  to the top with the other stdlib imports, since it doesn't depend on
  the `sys.path` fix; `warnings.filterwarnings("ignore")` itself stayed
  where it was

## First real CI run -- two real bugs found, both fixed

The first push (commit `d841cfa`) went red on both `test-fast` and
`test-full`. Diagnosed from the actual GitHub Actions logs (`gh run view
--log-failed`), not guessed at:

**Bug 1 -- `test-full` failed at test collection, before any test ran.**
`tests/test_api_shadow.py` imports `fastapi.testclient.TestClient`, which
(via `starlette`) now requires a package called `httpx2` to be installed.
`requirements-dev.txt` only listed `pytest`. Fixed by adding `httpx2` to
`requirements-dev.txt`, with a comment explaining why it's there.

**Bug 2 -- `test-fast` failed on the exact floating-point flake this
step's own local validation (above) claimed was resolved.** The real
GitHub Actions runner (`ubuntu-latest`, x86_64) hit the identical
`3.9999999999999996 == 4.0` failure in
`test_multistep_penalty_dilutes_a_single_step_spike_relative_to_a_sustained_plateau`,
using the exact same pinned `numpy==1.26.4` that had passed locally
minutes earlier. That disproves this step's own original claim (pinning
numpy fixes it) -- worth stating plainly rather than quietly editing the
history above. The real cause: `_compute_penalty_multistep`'s
`np.mean()` over ten identical values and `_compute_penalty`'s direct
scalar computation don't always take the same floating-point reduction
path, and that path can differ by CPU architecture (this session's local
venv ran on the arm64 dev machine; GitHub's runner is x86_64) -- a 1-ULP
difference, not a bug in the decision engine's math, and not something a
pinned package version can guarantee away, because it's about the CPU's
arithmetic, not the library's. **The actual fix**: changed the test's
assertion (`tests/test_decision.py`) from exact `==` to
`pytest.approx(...)`, which still verifies the two penalties are the
same value without demanding bit-identical rounding across
architectures. This is a more durable fix than the pinning explanation
this doc originally gave -- and a good, concrete lesson for anyone
reading this project's code afterward: floating-point equality across
different reduction paths (let alone different CPUs) is never
guaranteed, no matter how "obviously" two expressions are mathematically
equal.

Both fixes committed and pushed; the resulting CI run is what "Before ->
After" and "Still open" below now reflect.
